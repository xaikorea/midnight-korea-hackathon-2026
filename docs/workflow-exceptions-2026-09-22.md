# 예외 업무 절차 보완 — 2026-09-22

## 반영한 사용자 흐름

- 홈/진행 현황의 기업 연결 요청 → `/?view=access`에서 기본 기업 정보, 담당 업무와 소속 근거 입력 → 관리자가 승인 또는 반려.
- 신규 기업은 승인 시 생성한다. 기존 기업은 사업자 식별번호로 찾되 신청자에게 임의 기업 정보를 먼저 공개하지 않는다. 관리자는 기존 기업 수정 권한도 필요하다.
- 유효 자격은 있으나 본인 권한이 없는 경우 `missing_authority`로 구분한다. 신청 화면에서 기존 자격의 담당자 권한만 요청하고, 발급기관/관리자가 근거 확인 후 요청자의 로그인 ID에 30일 이내 권한을 연결한다. 기존 자격 만료일을 넘지 않는다.
- 검토 대기 → 보완 필요 → 증빙 선택/교체·보완 사유 → 재제출 → 검토 발급. 반려·철회 후에도 새 자료로 다시 제출할 수 있다. 최초 증빙과 각 변경 시점의 증빙 ID를 이력에 남긴다.
- 검토 요청 변경은 신청자만, 검토 의견은 발급기관/관리자만 처리한다. 기업별 기존 읽기·쓰기 및 증빙 권한 검사를 유지한다.
- 검토 revision과 상태를 대조하므로 오래된 발급 화면, 중복 검토, 다른 사용자의 철회를 차단한다. 서명 발급에도 최신 revision을 전달한다.
- 미충족은 경고 아이콘과 별도 제목, 기관 확인 대기는 대기 제목으로 표시한다. 최종 선정·계약 승인은 여전히 별도다.
- 가이드와 방문 페이지 허용 목록을 갱신했다. 기업용 기본 메뉴 5개는 유지한다.

## OpenFGA 기업 접근 권한 연결

관리자가 소속 근거 확인 체크와 검토 의견을 제출하면 먼저 승인 결정을 `provisioning` 상태로 D1에 저장한다. 그 후 고정된 두 관계 `business_writer`, `writer`를 신청자 및 승인 관리자에게 연결하고 신청자의 유효 접근 권한을 재확인한 뒤 `approved`로 전환한다. 기존 OpenFGA 모델을 사용한다. 서비스용 서버 토큰에는 해당 store의 check/write 접근 권한이 필요하며 브라우저에는 노출하지 않는다.

외부 서버 장애나 D1 최종 저장 충돌은 성공으로 표시하지 않는다. 관리자의 ‘접근 권한 연결 재시도’는 저장된 대상과 사용자로만 재실행한다. 이미 존재하는 관계는 다시 쓰지 않는다. 외부 권한 쓰기와 D1은 하나의 분산 트랜잭션이 아니므로 provisioning 중에는 일부 권한이 이미 존재할 수 있다. 승인 결정은 그 전에 영구 저장되며, 이 상태를 신청자 철회로 되돌려 이미 부여된 권한을 방치하지 않도록 철회를 막는다. 승인 후 접근 회수는 현재 OpenFGA 운영 도구에서 처리한다.

신청자는 해당 공동 공간의 company 역할이 미리 배정되어 있어야 한다. Keycloak 가입·공동 공간 멤버십 등록 자체를 공개 셀프 가입으로 바꾼 것은 아니다. 개인 공간의 요청은 다른 계정 관리자에게 전달되지 않음을 화면에서 안내한다. 발급기관/구매사/지원기관의 해당 기업 접근 관계는 기존 운영 권한 설정을 유지하며 자동으로 모든 기관에 문서 접근을 부여하지 않는다.

## 데이터 및 코드

- `lib/workflow-exceptions.ts`: 요청 생성, 소유권/역할/상태/버전 확인, 근거 있는 승인, 재제출 및 권한 서버 연결.
- `app/workflow-exceptions.tsx`: 기업 연결 양식, 권한 요청 양식, 관리자 검토 목록, 증빙 보완 양식.
- `lib/domain.ts`: accessRequests 및 확장된 issuanceRequests 상태/이력. 기존 JSON 저장 구조와 호환되며 별도 테이블 이관은 없다.
- `app/api/platform/route.ts`: 기존 CSRF·역할·CAS 저장 경로와 통합. 업무 감사 actor 기록 유지.

## 검증

- 전체 `npm run test:verification` 통과: 루트/SDK 타입 검사, validator 일치, 단위/API 21개 스크립트, Compact 10개, SDK 11개.
- `tests/workflow-exceptions.cjs`: 요청자/역할/버전 경계, 보완 이력, 철회/반려/재제출, 기업 연결 정보 격리, 중복 승인, 본인 권한 연결, OpenFGA 장애 후 재개. 외부 권한 서버/인증/DB는 fixture다.
- 실제 로컬 브라우저: 기업 연결 신청·관리자 승인 → 증빙 제출 → 발급기관 보완 요청 → 새 증빙 선택·재제출 → 최신 버전 발급 → 미충족 결과. 모바일 가로 넘침 검사.
- 브라우저에서 운영 권한 부족 분기는 사전 확인 응답 fixture를 사용하며 권한 요청·승인 자체는 실제 로컬 API를 호출한다. 실제 Keycloak 다계정 운영 검증으로 설명하지 않는다.

## 외부 통합의 남은 조건

이번 읽기 전용 preflight에서 preprod indexer는 응답했다. `127.0.0.1:6300` proof 서버는 응답하지 않았고 연결 지갑 정보가 없다. 따라서 실제 proof 생성·배포·거래 확정은 실행하지 않았다. 웹 자격 연결 및 실제 Compact 로컬 회로/SDK 테스트는 통과했지만 네트워크 완료와 다르다.

실제 운영 E2E에는 배포된 D1/R2, Keycloak 공동 공간 계정, 기업별 OpenFGA 관계, 필요 보호 서비스 설정이 필요하다. 외부 walt.id 지갑 및 KERIA/vLEI 실제 자격·서비스 검증도 해당 서비스와 자격이 필요하다. 무조건 성공하는 대체 응답이나 테스트 자격을 공인 자격으로 승격하는 처리는 추가하지 않았다.
