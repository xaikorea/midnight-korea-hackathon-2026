# 신청 처리 과정 관제

신청자의 세 단계 흐름을 유지하면서, 실제 백엔드 실행 내용을 별도 창에서 확인한다.

## 사용 방법

1. 공개 체험에 접속하고 신청 대상을 선택한다.
2. 공유 동의 후 제출하면 오른쪽에 **처리 과정 관제** 창이 자동으로 열린다. 창을 닫아도 이미 시작한 제출은 계속 처리된다.
3. **검사 결과·연결값 보기**에서 서명·발급기관·유효성·스키마 검사, 조건 판정, 자격 ID, 요청 ID, 정책/자격 SHA-256, 기관별 nonce를 확인한다.
4. 기관 필터로 구매사와 지원기관의 기록을 분리한다. 같은 자격을 사용해도 요청·nonce·제출 결과는 서로 다르다.
5. **별도 관제 창**(`/process`)을 열면 신청 화면과 나란히 볼 수 있다. 같은 공간의 기록을 3초 간격으로 조회하며, 숨겨진 탭의 주기적 조회는 생략한다.
6. 최근 20개 처리 기록을 다시 선택하거나 안전한 기록 JSON을 내려받을 수 있다. 새로고침 후에도 저장된 이력을 확인할 수 있다.

## 실제 실행과 표시의 관계

`submit-applications`의 `observe: true` 요청은 실제 처리 경계에서 NDJSON 이벤트를 스트리밍한다. 표시를 위한 인위적인 지연이나 가짜 완료 타이머를 사용하지 않는다. 짧은 작업은 즉시 끝날 수 있고, 그 경우 기록을 펼쳐 단계별로 확인한다.

| 단계 | 실제 실행 |
| --- | --- |
| 접근 권한·동의 | 역할, 기업 업무 쓰기 권한, 명시적 공유 동의 |
| 기업 자격 | 원본 전자서명, 현재 발급기관 신뢰, 취소·만료, 스키마, 기업 연결, 운영 모드의 담당자 권한 |
| 공유 내용 대조 | 동의 시점과 현재 자격·권한·정책의 해시 비교 |
| 기관별 요청 | 중복 접수/만료 검사, 정책 해시 및 nonce 연결 |
| 조건 판정 | 실제 설정된 로컬 엔진 또는 OPA 실행 |
| 결과 서명 | 원본 자격 해시를 포함한 기관별 결과에 Ed25519 서버 서명 |
| 기관 검증 | 기관이 자동 검증을 허용한 경우 서명·원본 연결·정책·nonce·판정 일치 재검사; 미허용이면 담당자 대기 |
| 감사 기록 | 접수·자동 검증·중복 요청 처리 기록 구성 |
| DB 저장 | 기존 버전 비교 저장(CAS)이 성공한 뒤에만 저장 완료 이벤트 전송 |

원본 속성, 비밀키, 토큰, 전체 서명, 증빙 바이트는 관제 기록에 포함하지 않는다. SHA-256·nonce와 서명 키 ID는 연결을 설명하는 값이다. 실제 Midnight 네트워크나 ZK 증명 실행으로 표시하지 않는다.

## 지속성과 예외 처리

- `application_process_runs` SQLite/D1 테이블에 처리 이력을 저장한다. 업무 데이터와 별도로 실패한 시도의 기록도 남는다. 자동 삭제는 없고 화면에는 최근 20건을 조회한다.
- 기록 저장은 기존 OpenBao 저장 보호 모드 설정을 따른다. 기존 SQLite 전체 백업 대상에 같은 DB의 새 테이블이 포함된다.
- 조회는 현재 로그인 공간으로 한정한다. 신청 기업은 자신의 실행만, 업무 관리자는 해당 공간에서 기업 조회 권한이 있는 실행만 볼 수 있다. 구매사/지원기관 역할이나 다른 방문자 공간에는 공개하지 않는다.
- 일부 기관 실패 시 성공한 기관만 기존 방식으로 저장한다. CAS 충돌이나 업무 저장 실패는 저장 완료로 표시하지 않는다.
- 중복 요청은 기존 접수를 반환하고, 새 서명/검증을 실행했다고 표시하지 않는다.
- 관제 기록 저장만 실패한 경우 업무 저장 결과와 구분하여 안내한다. 관제 화면 연결이 끊어지면 접수 상태를 다시 조회해야 한다.
- 종료 기록 없이 갱신이 멈춘 실행은 성공이나 실패로 추정하지 않고 마지막 갱신 상태를 안내한다.

검증: `tests/application-process.cjs`(스트리밍·저장 확정 순서·실패·재시도·권한·비밀정보 제외), `tests/application-process-ui.cjs`(실제 제출·창·모바일·별도 화면·이력·파일·사용자 격리).
